**Findings**

1. `CRITICAL` [torchft/checkpointing/rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:281), [rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:350), [rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:287)
The reader/writer fence from the plan is not actually implemented on the RDMA path. `send_checkpoint()` rotates `_previous_snapshot`/`_current_snapshot` and republishes the control record, and `disallow_checkpoint()` acquires the local `RWLock`, but no RDMA reader ever acquires a matching `r_lock()`. Unlike `HTTPTransport`, where the sender-side request handler wraps the whole transfer in `with _checkpoint_lock.r_lock()` ([http_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/http_transport.py:81)), `recv_checkpoint()` performs the entire RDMA read sequence with no sender-side participation. That means `disallow_checkpoint()` can return while a remote NIC is still reading the published snapshot, and the next `send_checkpoint()` can drop the last Python references to the old `RdmaMemory` objects by overwriting `_previous_snapshot`. This is the exact use-after-free hazard the plan was trying to avoid in the locking section.

2. `CRITICAL` [torchft/checkpointing/rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:218), [rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:221), [rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:623)
The “one transport instance per peer” requirement from the plan is not implemented. The code binds a single `_primary_transport`, never populates `_peers`, never uses `_PeerConnection`, and every incoming handshake calls `_primary_transport.connect(peer_addr)` on that singleton. The plan explicitly calls out that `RdmaTransport` has one virtual-circuit slot per instance, so reusing one sender transport for rank 1, rank 2, and later recovery rounds is not safe. In practice this means the advertised design for concurrent/multi-destination recovery is incomplete: one receiver can overwrite another receiver’s connection, and even the sequential 3-node/2-node recovery pattern from `transport_test.py` is not actually supported by the sender-side connection model.

3. `CRITICAL` [torchft/checkpointing/rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:250), [rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:605), [rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:647)
The TCP handshake server is not remotely addressable in a robust way. `_RDMABootstrapMeta` advertises only `handshake_port`, so the receiver guesses the host by decoding the opaque RDMA `bind_addr` bytes in `_extract_host_from_bind_addr()`, then falls back to `"localhost"` if parsing fails. The implementation itself comments that the bind address format is opaque, which makes this a correctness bug rather than a best-effort convenience. Cross-host recovery will fail whenever `bind_addr` is binary, not resolvable as a TCP hostname, or formatted as IPv6 (`[addr]:port` is returned unchanged and passed as the host string). The plan required a real side-channel for symmetric connect; this version does not publish enough information to make that side-channel reliable.

4. `WARNING` [torchft/checkpointing/rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:262), [rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:287), [rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:494), [rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:612)
The per-call `timeout` contract is effectively unimplemented on the RDMA path. `send_checkpoint()` ignores its `timeout` parameter entirely, `recv_checkpoint()` passes `timeout` into `_read_control_record()` but that helper never uses it, and the socket handshake uses `self._timeout` instead of the call-site timeout. More importantly, the blocking `transport.read(...)` calls have no timeout handling at all. The transport ABC and `transport_test.py` both treat timeout as a per-operation guarantee; this implementation currently only has a construction-time timeout for some local synchronization and TCP socket setup.

6. `WARNING` [torchft/checkpointing/rdma_transport.py](/home/mreso/Projects/torchft_torchstore_workspace/torchft/torchft/checkpointing/rdma_transport.py:359)
`shutdown()` does not retire the published snapshot generations or clear RDMA-registered state. The handshake thread is stopped, but `_current_snapshot`, `_previous_snapshot`, `_control_mem`, and any sender transport state are left live until Python GC happens to collect the transport object. On CPU this is sloppy; on GPU it can keep a large published snapshot resident longer than expected. Given the plan’s emphasis on explicit `RdmaMemory` lifetime management, shutdown should actively drop those references once new readers are impossible.

`_PeerConnection` and `_peers` are dead code in the current revision. Keeping the unused type around is not just style debt here; it makes the file look closer to the plan than it really is, even though the peer-pool behavior is absent.

**Top 3 Fixes**

1. Implement a real sender-side reader lifetime fence for RDMA reads, or an equivalent explicit reference-counted control path, so `disallow_checkpoint()` cannot return before remote readers are done with the published `RdmaMemory`.
2. Replace the singleton `_primary_transport` with an actual per-peer connection pool keyed by rank or peer identity, and make the handshake/connect path populate and reuse those peer transports.
3. Advertise a real TCP handshake address in bootstrap metadata instead of trying to derive it from the opaque RDMA bind blob, then add RDMA-path tests that exercise multi-peer connect, control-record transitions, and timeout/error handling.
